# 境界選定ルール

## 選定順序

必要な独立性を先に特定し、その独立性を満たす最も弱い境界を選ぶ。境界の物理的な強さを、設計の良さとして扱わない。

| 選択肢 | 得られる独立性 | 主なコスト | 選定条件 |
|---|---|---|---|
| 境界なし | なし | 最小 | 同じ理由・同じ時期に変わり、同じ単位でテスト・デプロイする。 |
| source-level分離 | 依存方向、責務、単体テスト、開発の分離 | 公開範囲、静的検査、DI | 論理的な分離だけで足りる。既定候補として最初に評価する。 |
| deployable component | リリース、バージョン、再検証の分離 | 互換性、パッケージ、リリース管理 | 別の周期でリリースまたは再利用する根拠がある。 |
| local process | メモリ空間、障害、起動の分離 | IPC、監視、起動順、デバッグ | プロセス隔離または異なる実行権限が必要である。 |
| network service | プラットフォーム、運用、チームの分離 | 通信失敗、分散データ、契約、観測、運用 | 独立運用・独立スケール・異種プラットフォームの便益が追加コストを上回る。 |

## 境界の実装形式

### 完全境界

- 相互に必要な入力/出力portと境界横断データを定義する。
- 各側を独立にコンパイルまたはデプロイできる。
- 強い隔離を得る代わりに、契約・変換・互換性の維持コストを負担する。

### 一次元境界

- 利用側が所有する一方向のportで実装を差し替える。
- 将来の完全境界への余地を残すが、逆向きの抜け道を規律または静的検査で防ぐ必要がある。

### Facade

- 呼び出し面を単純化する。
- 内部実装への推移的依存や抜け道を防がない。隔離の証明として扱わない。

## serviceを選ぶ前の反証

- 共有データモデルの変更で複数serviceを同時に変えないか。
- 同期通信、再試行、タイムアウト、冪等性、順序、部分失敗を追加していないか。
- 独立デプロイの実績または明確な予定があるか。
- 観測、認証認可、契約互換性、オンコール責任を引き受けられるか。
- source-level分離またはdeployable componentでは満たせない要件があるか。

一つでも未確認なら、serviceを既定案にしない。
