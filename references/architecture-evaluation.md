# アーキテクチャ評価規則

## 二次元分離

component候補は、次の二軸を重ねて作る。

1. **変更理由:** actorまたはuse caseごとに、同時に変わる規則をまとめる。
2. **policyのlevel:** 入出力に遠い高水準policyを、UI、DB、SDK、通信、表示形式などの低水準詳細から守る。

`controller`、`presenter`、`interactor`は役割であり、単独でcomponent境界を決めない。actor/use caseが異なれば役割内でも分け、同じ理由で変わるなら役割をまたいで同じ成果物にまとめることを検討する。

## componentの成立条件

componentには、少なくとも次を記録する。

- 公開契約と利用側
- 依存先と逆依存の影響範囲
- ビルド単位とテスト単位
- リリース単位、互換性条件、バージョン方針
- 所有チームまたは責任者

単に同じディレクトリにあること、または同じ言語機能を使うことはcomponentの根拠にならない。独立した検証またはリリースの必要性がないなら、source-level分離に留める。

## 変更コストのオラクル

変更案ごとに、次の前後差を比較する。

| 項目 | 確認方法 |
|---|---|
| 変更対象 | 編集が必要なmodule、contract、設定の数と関係性 |
| 再検証範囲 | 実行するtest、結合検証、互換性検証 |
| 調整作業 | 同時に意思決定またはリリースするteam/component |
| 運用負荷 | 監視、障害対応、設定、データ移行、互換性管理 |

小さな要求に対してこれらが増え続けるなら、構造が変更要求の形に適合していない候補として扱う。見積もりだけで断定せず、履歴、依存グラフ、テスト結果、リリース手順で裏付ける。

## 可変状態と並行性

可変状態を扱う境界には、次を記録する。

- 状態名と不変条件
- 唯一の所有component
- 更新者と更新API
- 同時更新の規則: 排他、楽観的制御、トランザクション、順序、再試行、冪等性
- 障害時の回復、再構築、監査
- 性能とストレージの制約

可能な計算を不変なpolicyへ寄せ、可変状態とその同期を狭いcomponentに閉じ込める。event sourcingは、履歴保存、再構築、ストレージ、処理時間、運用の制約を満たす場合だけ比較候補にする。既定解として導入しない。

## falsifiabilityとテスト

テストは正しさを証明しない。設計上の主張、依存規則、境界、状態遷移について、誤りを発見できる反例を探す。

- use caseごとに、正常系だけでなく、不正入力、境界値、失敗した外部I/O、並行更新、契約違反を反証候補にする。
- componentとserviceを、外部詳細なしに反証できる小さな単位へ分解する。
- E2Eの成功を内側のpolicyの正しさの証明にしない。unit、component、契約、E2Eを、それぞれ異なる反証目的に使う。
- テストが落ちた場合は、最初に設計主張、契約、境界、実装のどれを反証したのかを記録する。

## componentの凝集・安定性・成熟度

componentの構成には、次の相反する圧力がある。

- **common closure:** 同じ理由・同じ時期に変わるものをまとめ、変更・再検証を局所化する。
- **common reuse:** 利用側に不要なものを依存させず、不要な再コンパイル・再デプロイを避ける。
- **reuse/release equivalence:** 再利用する単位は、理解できる変更履歴と互換性を持つリリース単位にする。

開発初期はcommon closureを優先し、再利用者や独立リリースが増えた段階でcommon reuseとrelease境界を強める。component構成を恒久の正解として固定しない。

安定したcomponentほど抽象的な契約を持ち、変化しやすい実装はそこへ依存させる。安定かつ具体的なcomponentは変更を妨げ、抽象的だが誰にも依存されないcomponentは不要な候補になる。依存数・抽象度の数値は調査の補助であり、最適化目標や合否判定として扱わない。

## 境界の監視と再評価

境界は初期設計で一度決めて終わりにしない。次の兆候を収集し、境界を強めるか、弱めるか、維持するかを定期的に判断する。

- 小さな変更が複数actor、component、releaseへ波及する。
- 一時的な例外依存、特例分岐、共有DTOが増える。
- component間の同時デプロイまたは互換性調整が恒常化する。
- 独立したテスト、ビルド、運用ができない。

実装コストと無視した場合の変更コストが逆転する兆候を、境界の再設計を開始する条件として扱う。

## serviceとhardware/platform依存

service境界は、その内部がcomponentとDependency Ruleで設計されている場合にだけ、アーキテクチャ境界になりうる。横断的関心事はservice間ではなくservice内部のcomponentを横切る場合がある。serviceを小さなmonolithとして扱わない。

対象が組み込み、端末、OS固有API、DB方言、または専用deviceを含む場合は、hardware/platform依存をadapterへ隔離する。protocol解析やuse caseをdevice driverと同じmoduleに置かない。target hardwareなしでユースケースをテストできることを確認する。
