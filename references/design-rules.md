# 設計診断ルール

## 分類

| 区分 | 責務 | 依存してよい対象 | 典型的な禁止依存 |
|---|---|---|---|
| ドメイン方針 | 事業全体の規則、不変条件、計算 | 同区分の方針 | HTTP、ORM、DB、UI、SDK、フレームワーク |
| アプリケーション方針 | ユースケースの進行、入力/出力ポート、アプリケーション固有の規則 | ドメイン方針、同区分 | HTTP、ORM、DB、UI、SDK、外側で宣言されたポート |
| インターフェースアダプター | 外部形式と内側形式の変換、Controller、Presenter、Gateway実装 | アプリケーション方針、ドメイン方針、同区分 | 原則なし。ただし、別のアダプター内部への不要な結合 |
| フレームワーク/ドライバー | HTTP、DB、ORM、メッセージング、SDK、CLI、composition root | すべての内側区分 | 内側の方針を外側の型・設定へ従属させる設計 |

## 違反候補

### 依存方向

- ドメイン方針またはアプリケーション方針が、HTTP、ORM、DB、UI、SDK、フレームワークの型をimportまたは公開APIに含める。
- 内側が、外側で定義した具体的な実装またはインターフェースを参照する。
- 境界を越えて、DB行、HTTP request/response、ORM entity、フレームワーク生成型をそのまま渡す。

### ユースケースの迂回

- Controller、ジョブ、イベントハンドラーが、ユースケースを通らずに永続化や外部Gatewayへ直接アクセスする。
- 認可、検証、トランザクション方針が複数の入出力経路に複製される。

### 責務と変更

- 同一モジュールに、異なる変更アクターの規則が混在する。
- 変更要求ごとに無関係なテスト、クラス、チームの作業が連鎖する。
- 技術別の上位パッケージだけが見え、主なユースケースを特定できない。

### コンポーネント依存

- コンポーネント依存グラフに循環がある。
- 一つのコンポーネント変更が、関係のないコンポーネントの同時リリースを常に必要とする。

### テスト

- ビジネス規則を証明する唯一のテストがGUIやネットワークを経由する。
- テストがプロダクションのクラス・メソッド構造に一対一で結合し、内部リファクタリングで大量に壊れる。

## 解消パターン

- 内側にportと入出力モデルを置き、外側がadapterとして実装する。
- 外側形式をadapterで内側形式へ変換する。
- 変更アクターまたはユースケース単位へ責務を分割し、必要ならFacadeで呼び出し面を安定させる。
- composition rootに具体実装の選択とDI登録を集める。
- ユースケースを直接呼び出すテストを追加し、UI/E2Eテストは統合確認へ限定する。
- 依存ルールを静的解析またはアーキテクチャテストへ移す。

## 原則を使う診断質問

| 原則 | 診断質問 | 過剰適用の兆候 |
|---|---|---|
| SRP / CCP | 同時に変わる規則と変更アクターは何か。 | クラス数や関数数だけを理由に分割する。 |
| OCP | 新しい変動が高水準policyの変更を必要とするか。 | 現実の変動軸なしに拡張点を量産する。 |
| LSP | 代替実装は利用側の特例分岐なしに契約を満たすか。 | 実装差を隠せず、呼び出し側が型判定する。 |
| ISP / CRP | 利用側は不要な操作・依存・再デプロイを負うか。 | 操作ごとに極小interfaceを増やし、契約の全体像を失う。 |
| DIP | 内側が依存する具体物は変わりやすいか。portの所有者は利用側か。 | 安定した標準ライブラリまで抽象化する。 |

## port/adaptorの規則

- portは実装側ではなく、利用側の高水準policyが所有する。
- use case入力と出力は、内側の語彙で定義する。
- HTTP request/response、ORM entity、DB行、SDK型を境界の内側へ渡さない。
- Gatewayは汎用CRUDではなく、ユースケースに必要な操作を表す。
- Presenterは出力モデルをview modelへ整形し、Viewに判断を持ち込まない。
- composition rootは具体実装、設定、DI、外部資源の生成を担当する。

## 反証質問

- この抽象化を削除すると、実在する変更要求を安全に実装できなくなるか。
- interfaceは利用側の必要を表すか、それとも一実装のメソッド列挙か。
- DTOは内側の語彙を表すか、外側の型を写経しているだけか。
- component間で同じデータモデル、同じリリース、同じチーム調整を常に必要としていないか。
- service分割が共有データ、同期通信、分散トランザクションを増やしていないか。
- frameworkのannotation、base class、ORM entityがdomain/use caseへ侵入していないか。
- UI E2Eの成功をユースケースのテスト可能性の証明として誤用していないか。

## 例外の記録

例外には、依存元、依存先、例外の理由、影響、撤去条件、見直し時期を記録する。将来の抽象化を予想するだけでは例外の根拠にしない。
